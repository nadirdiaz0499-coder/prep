On-Call & Prevention Strategy

The Question: "If you're worried about multiple enrollments overloading the server, what would you actually do to prevent it?"

Your Answer (Be specific, not theoretical)

1. Monitoring (The Eyes)

  • Set up alerts on Jamf/MDM server: CPU usage, memory usage, enrollment queue depth
  • Real-time dashboard showing: "How many devices are trying to enroll right now?"
  • If queue is growing faster than devices are enrolling, alert fires

2. Throttling (The Governor)

  • Don't let unlimited devices enroll simultaneously — set a limit
  • Example: "Only 5 devices can enroll at the same time. The rest wait in queue."
  • This prevents the server from getting hammered

3. Capacity Planning (Know Your Limits)

  • Test beforehand: "Our server can handle ~50 concurrent enrollments before it chokes"
  • Document it: "If we're on-boarding 200 people in Colombia, spread it over 4 days, not 1 day"
  • Plan for it, don't discover it at 3 AM

4. Runbooks (If It Happens Anyway)

  • Have a documented playbook:
    • Step 1: Check Jamf server health (CPU, memory, disk space)
    • Step 2: If queue is backed up, throttle enrollments manually
    • Step 3: Notify users: "Devices will enroll in ~30 mins, please be patient"
    • Step 4: Monitor until queue clears

5. Communication (Prevent Panic)

  • If enrollments are slow, users might keep restarting their devices
  • Send a proactive message: "We're on-boarding 50 devices today. Your device will enroll automatically. You don't need to do anything."
  • This prevents users from making it worse
"I'd set up monitoring on the MDM server to watch CPU, memory, and enrollment queue depth. If the queue gets too deep or server resources spike, I'd get an alert. I'd also throttle enrollments — maybe only 5 devices at a time — so we don't overwhelm the server. And I'd have a runbook: if something does go wrong at 3 AM, I follow the steps, I don't improvise. The key is investing upfront so 3 AM calls don't happen in the first place."

Why This Matters:

  • Shows you're not just reactive (waiting for the fire)
  • You're proactive (preventing the fire)
  • You have a system (monitoring + throttling + runbooks)
  • You communicate (users aren't surprised)

Bash Scripts & Technical Depth

The Question: "Tell me about a Bash script you actually wrote for Jamf."

Your Real Example (Use this)

At Metsa, I wrote a script that deployed Adobe Creative Suite and verified it installed correctly. Here's what it did:

What the script did

  1. Check if Adobe was already installed (no point reinstalling)
  2. If not installed, download from our internal repository
  3. Run the installer silently (no user prompts, just installs in background)
  4. Verify the installation succeeded (check if the app is in /Applications)
  5. If it failed, log the error and notify us (so IT knows it didn't work)
  6. If it succeeded, log it (for compliance audits)

Why it was tricky

  • Adobe installers sometimes fail silently — you think it installed, but it didn't
  • The script had to catch errors and report them back so I'd know which devices had problems
  • I had to make sure the script ran as root (admin level) or it wouldn't have permission to install
  • Logging was critical — if a compliance audit asked "was Adobe installed on Device X on Date Y?", I had to prove it via logs

A simplified version of the logic

If Adobe is installed → skip (don't reinstall)
Else → download from repo → install → check if /Applications/Adobe exists
  If exists → log "Success"
  If not exists → log "Failed on Device $(hostname)" and alert IT

Key learning

  • Bash scripts aren't about being fancy — they're about solving real problems
  • In this case: "How do I deploy software to 35 devices without doing it manually 35 times?"
  • The script also meant I could track what was installed where, which was huge for compliance
"I wasn't writing complex scripts. I was automating repetitive tasks. The Adobe deployment is a good example — instead of manually installing on each device, Jamf runs my script, and I get a log telling me which devices succeeded and which failed. That's where the value is: automation + visibility."

If David asks follow-ups

  • "Did you use any error handling?" → YES. The script checks if the app exists and logs failures.
  • "How do you know if it failed?" → Logs. I check Jamf logs and look at the exit code.
  • "Ever had a script break something?" → Honestly, you learn to test in a test environment first. That's IT 101.

Q2: Debugging Jamf Custom Trigger Silent Failures

Question: "If a Jamf Custom Trigger script exits with code 0 but the action didn't actually complete, how would you debug that?"

Best Answer:

"If a script exits with code 0, Jamf thinks it succeeded even if the script's internal logic silently failed. My first step is to isolate whether the issue is in Jamf's execution context or the script itself. I go to the client, check the Jamf logs for stdout and stderr to see what actually happened. Then I review the policy history in Jamf Pro to confirm what parameters were passed. After that, I focus on common culprits: context issues—the script runs as root but modifies user preferences, or there's an environment variable problem. I verify it uses absolute paths, not relative commands. If nothing obvious appears, I manually run the script on the machine with verbose output to see exactly where it breaks. Then I update the script to explicitly capture non-zero exit codes so Jamf properly reports failures in the future."

Why this works: Shows deep Jamf knowledge, debugging methodology, and that you don't just rerun scripts blindly.

R3-Q1: Most complex infrastructure project

Question: "Walk me through your most complex infrastructure project — something you designed, implemented, and had to troubleshoot when things went wrong."

"At Metsa I owned endpoint compliance for a fleet that grew from about 30 to 40 devices, mostly MacBooks plus some Windows PCs, with a very small IT team. The goal was to enforce FileVault encryption and a standard app baseline through Jamf Pro and Intune without checking devices by hand. I built custom Extension Attributes in Jamf to collect data Jamf doesn't gather by default, like FileVault status and browser version, and fed them into Smart Groups. Any non-compliant device flagged itself automatically. Then, after one policy push, a group of MacBooks stopped checking in and silently dropped out of compliance reporting. I isolated it on a test machine: profiles status -type enrollment to confirm the MDM profile was still there, sudo jamf checkJSSConnection for server connectivity, and /var/log/jamf.log to find the failure. Root cause: the Jamf binary had stopped communicating after a background macOS update. A manual sudo jamf policy plus re-pushing the configuration profile restored check-in, and FileVault status reported correctly again. The lesson: an assigned profile doesn't mean the local agent is actually checking in. So I created a Smart Group that flags any device with no check-in for 48 hours. That became our early warning for silent failures before they turned into compliance gaps."

Key commands to remember: profiles status -type enrollment · sudo jamf checkJSSConnection · sudo jamf policy · sudo jamf recon (force inventory update) · /var/log/jamf.log

R3-Q2: Google Workspace — first 30 days for a new org

Question: "Walk me through how you'd implement Google Workspace for a new organization. What would your first 30 days look like?"

"I've worked with Workspace at PwC, and the identity principles are the same on any platform: structure first, then access, then integrations. In 30 days the goal is a secure foundation, not perfection. Days 1–10, foundation: an OU structure by department and location, for example a Colombia OU, so policies can differ by team. Enforce 2-Step Verification tenant-wide from day one. Configure SPF, DKIM and DMARC so nobody can spoof our domain. Keep super admin to two named people plus a break-glass account, and use delegated admin roles for everything else. Days 11–20, access: group-based access for distribution lists, shared drives and app access, never permissions on individual accounts. A standard onboarding and offboarding checklist in Jira: account, OU, groups, license on the way in; suspend, transfer Drive data, revoke tokens, remove from groups on the way out. Days 21–30, integration and hygiene: connect Workspace identity with device management in Jamf and Intune, turn on audit log alerts for suspicious logins and admin changes, review third-party OAuth app access, and put a backup in place for Drive and Gmail. The lesson I've learned: permissions on individual accounts turn into a mess when people change roles. OUs and groups from day one prevent orphaned access and make audits much easier."

R3-Q3: Saturday night — super admin access left open

Question: "Second week in Colombia ops, 15 hires onboarding next week. Saturday night you find super admin access given to several people who shouldn't have it, including a contractor who no longer works here. SOC 2 gap. What do you do in the next 2 hours?"

"I treat it as a live security incident, not a Monday ticket. A former contractor with super admin is active exposure. First, I post in the on-call channel to the security lead and my manager that I'm acting. For a change this sensitive, I don't want to act silently. Step 1, contain: suspend the former contractor's account, sign out all sessions, reset the password, and revoke OAuth tokens and app passwords. Step 2, reduce: for current employees with super admin, I downgrade anyone who clearly doesn't need it to the minimum delegated role. If I'm not sure whether someone depends on that access, I flag them for a Monday review with their manager instead of breaking something on a Saturday night. Super admin stays with named leads plus a break-glass account. Step 3, investigate: pull the admin and login audit logs for the last 30 to 90 days. I look for new admins, data exports, mail forwarding rules, new OAuth apps and 2SV changes, especially from the contractor's account. If I find signs of misuse, it becomes a full incident response. Step 4, protect Monday: verify the onboarding setup for the 15 hires is untouched, meaning accounts, OUs, groups and the Jamf PreStage enrollment. Step 5, document: a timeline with timestamps, every change, and what the logs showed. I send a summary to the security lead and manager and open a Jira ticket as SOC 2 evidence. Why this works: Contain first, don't break the business, escalate early, leave an audit trail, fix the root cause.

R3-Q6: New MacBook skipped Jamf enrollment, user starts in 2 hours

Question: "A new hire in Colombia gets a MacBook shipped home, finishes Setup Assistant, reaches the desktop, but never enrolled in Jamf. No apps, no FileVault, no profiles. They start in two hours. What do you do?"

"That's a zero-touch enrollment failure. If the Mac were correctly assigned in Apple Business Manager with a PreStage scoped to it, Setup Assistant wouldn't have let them skip enrollment. So something in the assignment chain broke. I work two tracks: unblock the user, and fix enrollment. Unblock: I reassure the user and have them log into Google Workspace in the browser with MFA, so they can join day-one meetings while I work. Diagnose on my side first, it takes a minute: is the serial number in Apple Business Manager? Is it assigned to our Jamf MDM server? Does it show up in the Jamf PreStage enrollment and is it scoped? They accept the notification, and the Jamf profile installs. If that doesn't work, since it's a brand-new Mac with no data, I have them run Erase All Content and Settings. It goes back to Setup Assistant and ABM forces enrollment on activation. That's also cleaner for security, because the local admin account they created was never managed. Verify: in Jamf I check inventory, FileVault is enabled and escrowed, profiles are installed, and core apps landed. Then prevent it: find out why it happened. Usually the device was bought outside our ABM-linked reseller, or it was never assigned. I'd add a pre-shipping check: every serial confirmed in ABM and in the PreStage before it leaves, and the PreStage set so enrollment is mandatory and the MDM profile can't be removed."

Key facts: sudo profiles renew -type enrollment (re-triggers ADE) · profiles status -type enrollment (checks enrollment state) · Erase All Content and Settings = macOS 12+ on Apple silicon / T2 · Mac bought outside ABM can be added with Apple Configurator for iPhone (requires an erase)

Agile refresher for R3-Q5 (know these cold)

  • Sprint: fixed work cycle, usually 2 weeks
  • Backlog: prioritized list of pending work. Grooming/refinement = reviewing and estimating it
  • Story points: relative effort, not hours. Usually Fibonacci: 1, 2, 3, 5, 8, 13. Big number = more complex/uncertain → split it
  • Epic → Story → Task/Sub-task: big initiative → deliverable piece → concrete step
  • Ceremonies: Sprint planning (what we commit to), Daily standup (yesterday / today / blockers), Sprint review (show results), Retro (what to improve)
  • Velocity: points a team completes per sprint, used to plan the next one
  • Jira Service Management (JSM): Jira's ITSM product. Has queues, SLAs, request types, portal = the ServiceNow equivalent. "ITSD" in the JD = IT Service Desk project
  • Kanban vs Scrum: Kanban = continuous flow with WIP limits (common for support queues). Scrum = fixed sprints (common for project/backlog work). Sezzle likely uses both: tickets as flow, initiatives in sprints

Short Scripts: Technical Scenarios (say it like this)

Rule: 45–75 seconds. Say the key points, then: "Happy to go deeper on any of those." Let them ask follow-ups.

S1: Mac hasn't checked in to Jamf for 12 days

"So first I'd check if it's just this Mac or other devices too, because if it's several, it's probably a server or network issue, not the laptop. If it's just this one, I'd get on a call with the user, check the basics like the network and the date and time, and then have them open Terminal. I'd run jamf checkJSSConnection to see if it reaches the server, force a check-in with jamf policy, and look at the jamf.log to see where it fails. Then profiles status to confirm it's still enrolled in MDM. To tell the two cases apart: if the connection works and the MDM profile is there, the daemon is just stuck. I run jamf manage and a recon, and it comes back. But if I see a device signature or certificate error, or the MDM profile is gone, it lost trust with the server, and the fix is re-enrolling with profiles renew, or worst case, wipe it and let it enroll again. And after that, I'd set up an alert for devices that haven't checked in for a couple of days, so we don't find out after twelve. Happy to go deeper on any of those steps."

If they dig: Jamf has two channels: the binary (policies, packages, inventory, checks in ~every 15 min) and MDM/APNs (profiles, commands). Send an Update Inventory MDM command from the console: completes = MDM OK, problem is the binary; stays pending = MDM broken too. Also check: disk full, wrong clock, VPN/proxy. Commands: sudo jamf checkJSSConnection · sudo jamf policy -verbose · sudo launchctl list | grep jamf · sudo profiles status -type enrollment · sudo profiles list · log show --last 1d --predicate 'process == "mdmclient"' · sudo jamf manage · sudo jamf recon · sudo profiles renew -type enrollment · logs: /var/log/jamf.log, /var/log/install.log

S2: Friday 4:30 PM, high-security user terminated for policy violation

"First thing, I'd coordinate with HR on timing. Ideally I cut access while they're on the call with the person, not before and not after. Then identity first, because that's the front door. In Entra ID, I block sign-in and revoke all their sessions, so every single sign-on app is cut off. In Google Workspace, I suspend the account, sign them out everywhere, reset the password, and revoke app passwords and third-party tokens. I remove them from any groups with access to financial data, and any shared credentials they knew get rotated. For the Mac, I send a remote lock from Jamf, not a wipe. It's a policy violation, so there might be an investigation, and wiping would destroy evidence. The data's already protected because FileVault is on. Then we arrange to get the device back. The whole time, I'm logging timestamps for every step. For SOC 2, that's the proof access was removed right away. After that, I review audit logs for any unusual downloads or sharing."

Key point: LOCK, don't wipe (evidence). If they dig: Entra access tokens can stay valid up to ~1 hour, so also revoke sessions directly in critical apps.

S3: EDR update triggers Full Disk Access / system extension prompts

"macOS doesn't let an app get Full Disk Access or system extensions unless someone approves it. Without admin rights, the only way is for Jamf to approve it ahead of time with configuration profiles. So either the profiles were missing, or the new version needed something the old profile didn't cover. First, I'd pause the rollout. Then I'd push the right profiles: one for Full Disk Access, and one that allows the vendor's system extension. The vendor usually documents exactly what's needed. Once they're installed, I re-run the install. The user doesn't touch anything. For the future: profiles always go out before the app, and I test every update on a Mac with a normal user account, not an admin one. If the popup shows up there, it never reaches users."

If they dig: Full Disk Access = PPPC profile (Privacy Preferences Policy Control), built with Jamf's PPPC Utility. System extensions = System Extensions payload, allowed by the vendor's Team ID. Scope the install policy to a Smart Group of Macs that already have the profile. Verify with profiles list and systemextensionsctl list.

S4: 5 engineers start in 3 weeks, MacBooks backordered 5 weeks

"First, I'd tell HR and the engineering manager right away, so there are no surprises in three weeks. Then I'd look for Macs in this order. One, other authorized resellers in Colombia linked to our Apple Business Manager. Two, a different model or configuration that's in stock now, if the engineering manager agrees it works. Three, devices we already have: the buffer stock, or laptops from people who left, wiped and redeployed. Whatever we get has to be in Apple Business Manager, so it enrolls automatically. I wouldn't ship from Mexico, because customs could take longer than the backorder. If we still come up short, I prioritize who needs a Mac on day one, and the rest start onboarding in Google Workspace for a few days. What I wouldn't do is let them use personal laptops on company systems."

S5: CIS controls on a Mac fleet

"CIS controls are a prioritized list of security practices. SOC 2 and PCI tell you what you have to prove, and CIS gives you a practical way to get there. For Macs, there's also the CIS benchmark with specific settings. I'd start with the basics: know every device and app we have, which Jamf inventory gives us. Then a secure baseline pushed through Jamf: FileVault, firewall, screen lock, no local admin. I wouldn't build it by hand. There's an open-source project, the macOS Security Compliance Project, that generates the Jamf profiles mapped to the benchmark. Then Smart Groups catch any Mac that drifts, like someone turning off the firewall. And the same reports become our audit evidence."
